# Milestone 2B — local staff management and persistent face enrollment

## Delivered workflow

Admin login → Staff list → Add Staff → Staff Profile → Enroll/Re-enroll Face → saved confirmation on Staff Profile.

The staff list observes Room changes and displays each name, employee ID and enrollment status. It has an empty state, loading/error/retry states, Add Staff, profile navigation and Sign out. Add Staff validates required fields, prevents repeated submissions, handles duplicate IDs and navigates directly to the new profile. Missing profile/enrollment IDs show “Staff member not found” with a Back action.

Enrollment reuses the existing CameraX → ML Kit → orientation/alignment → MobileFaceNet pipeline. The button disables during capture/inference/save. Exactly one detected face is required. Camera permission denial and settings recovery, camera binding failures, no/multiple faces, missing staff, model/inference errors and save failures are handled. Only successful inference is persisted. Re-enrollment overwrites that staff row's embedding, model fingerprint and enrollment timestamp in one UPDATE; failed attempts leave the existing enrollment intact.

A successful save pops enrollment off the back stack and displays “Face enrollment saved successfully” on the profile. Profile/list status comes from the repository's Room Flow. The confirmation can be dismissed and is cleared before the next enrollment attempt. Enrollment images/crops are discarded; no enrollment selfie is written to disk.

No staff authentication, attendance marking, location, attendance photos or attendance table were added. MainActivity and the face model, preprocessing and matching threshold are unchanged. The POC is visibly grouped under “Debug tools” and is only registered/displayed in debug builds.

## Database schema

Room database file: application-private `databases/attendai.db`. Version **1**. One entity/table: `staff`.

| Column | SQLite type | Nullable | Meaning |
|---|---|---|---|
| `id` | INTEGER primary key, autoincrement | No | Local database identifier used in typed routes |
| `employeeId` | TEXT, unique index | No | Trimmed and uppercased with Locale.ROOT |
| `name` | TEXT | No | Trimmed display name |
| `faceEmbedding` | BLOB | Yes | 128 normalized IEEE-754 float values |
| `faceModelId` | TEXT | Yes | SHA-256 fingerprint of the bundled MobileFaceNet export |
| `faceEnrolledAt` | INTEGER | Yes | Enrollment/re-enrollment time, Unix epoch milliseconds |

`isFaceEnrolled` is derived from the three enrollment fields being present; there is no redundant stored boolean. New staff have all three fields null. There is no attendance table or premature schema for it.

The exported Room schema is checked into `app/schemas/com.divanshgandhi.attendai.data.local.AttendAiDatabase/1.json`. This is the first database version, so there is no migration yet. No destructive-migration fallback is enabled; subsequent schema changes will need an explicit migration.

Employee IDs are case-insensitive at the repository boundary because every creation is canonicalized: `emp-01` and ` EMP-01 ` both become `EMP-01`. A pre-check gives a useful error and the SQLite unique index prevents simultaneous duplicate inserts. Inserts use ABORT, never REPLACE, so a duplicate cannot erase an existing face enrollment.

## FloatArray storage

`EmbeddingConverters` stores one float as four little-endian bytes. A 128-dimensional embedding occupies **512 bytes** with no string/JSON rounding. Null stays null. The converter reconstructs the FloatArray on reads and rejects malformed byte counts.

The repository validates dimension 128 and finite/nonzero values, then uses the existing `FaceMatcher.normalize`. DAO reads/entity inserts use the Room type converter. The enrollment UPDATE accepts an explicit `ByteArray` generated by the same converter, because Room expands primitive array query parameters as SQL lists otherwise. The BLOB and its model/timestamp metadata are updated atomically.

Model fingerprint: `4a5cfa4491ca0b02d4ea1552b808568b1569921d999b36c82b79def393d116ea`. Fingerprinting makes the representation identifiable for a later model migration; it does not implement future attendance matching.

Data survives activity recreation, force-stop and process restart. Sign out clears only the session. Uninstall/clear app data removes local staff. Android backup is disabled and database domains are explicitly excluded from cloud backup/device transfer to keep this local biometric data on this installation. Database encryption/key management is not part of this assignment milestone; storage uses Android's app sandbox.

## Architecture and dependencies

Compose screens → feature ViewModels → `StaffRepository` → `RoomStaffRepository` → `StaffDao` → Room.

`StaffEntity` is also the small read model exposed by this repository, avoiding unnecessary DTO/mapping layers. No Compose screen or ViewModel accesses a DAO. `AppContainer` owns one database/repository instance; the existing manual factory supplies ViewModels and resolves typed route IDs via SavedStateHandle. No Hilt or backend was added.

`CameraCapturePanel` extracts the existing preview/permission controls for both enrollment and the Debug POC. It owns camera lifecycle/UI concerns. `FaceEnrollmentProcessor` is a narrow test seam implemented by the **existing** `FaceRecognitionEngine`; its enrollment method invokes the same extraction pipeline, returns the embedding and releases the crop. The production factory always supplies that real engine. Test doubles are used only in deterministic ViewModel unit tests; real-engine instrumentation tests remain included.

Camera decode remains on CameraX's worker executor; detection/alignment/model work remains on Dispatchers.Default. Room suspend queries/Flow handle database work off the main thread. Native engine cleanup is serialized with in-flight operations.

Added through the version catalog: Room runtime/compiler/plugin **2.8.5** and KSP **2.3.10**. The Room Gradle plugin exports schema history; no optional Room adapters/testing runtime or new DI library was needed. References: [Room release/dependency documentation](https://developer.android.com/jetpack/androidx/releases/room), [KSP documentation](https://kotlinlang.org/docs/ksp-overview.html).

Verified on the Pixel 7 emulator:

- Debug APK builds successfully; the final APK was installed and opened on Pixel 7.
- **32 unit tests passed**, zero failed/skipped: existing 18 plus 3 converter tests and 11 Admin ViewModel tests.
- **16 instrumented tests passed**, zero failed/skipped: existing 8 plus 6 real Room/repository tests and 2 Admin navigation tests.
- Lint: **0 errors, 23 warnings**. Warnings are existing template resources/redundant label and available dependency/tool updates. No lint suppression or baseline was added.

Coverage includes blank field validation, duplicate employee IDs (including concurrent writes and database-index enforcement), field normalization, repository reads/errors, loading/submission state, repeated taps, missing IDs, successful enrollment state, failed re-enrollment retaining old data, retry, exact FloatArray round-trip, enrollment replacement and disk database reopen.

The real MobileFaceNet instrumentation test generates a photographic-fixture embedding through the production engine, saves it with the production repository, closes/reopens the file-backed database and verifies the restored vector still matches. Navigation tests use the real navigation graph and Room repository with an isolated in-memory database; repository tests use uniquely named temporary database files. They do not seed or clear the user's staff database.

The camera smoke test now tolerates either synthetic or webcam input: each capture must finish with an embedding or an explicit face-quality rejection. Deterministic no-face/multiple-face assertions remain in photographic pipeline tests. No mocked recognition is wired into the application.

## Exact manual emulator test steps

1. Open the project in Android Studio and sync Gradle. Select the **app** configuration, **debug** variant and **Pixel 7** device. Keep the already validated **Front camera → Webcam0** configuration; start/cold-boot the AVD if needed. Run the app. Do not uninstall or clear data during persistence testing.
2. Sign in as **Admin**, username **admin**, password **admin123**. On a fresh install expect “No staff yet. Add your first staff member.” The “Debug tools” section is separate from Add Staff.
3. Tap **Add Staff → Save Staff** with blank fields. Expect “Enter a name” and “Enter an employee ID.” Enter **Name: Alex Demo**, **Employee ID: emp-001**, then **Save Staff**. Expect **Staff Profile**, **Employee ID: EMP-001**, **Face Not Enrolled**, and **Enroll Face**.
4. Tap **Back → Add Staff**. Enter another name with **Employee ID: ` EMP-001 `**. Tap **Save Staff**. Expect “That employee ID already exists,” with the form retained. Change the ID to **EMP-002** and save; expect the second staff profile. Return to the list and open **Alex Demo**.
5. Tap **Enroll Face**. Deny camera access first if prompted: the screen should show permission guidance and no capture action. Tap **Grant camera access**, or **Open app settings → Permissions → Camera → Allow only while using the app**, then return. If already allowed, permission denial can be tested by changing that app setting and reopening the screen.
6. With exactly one face, good light and a near-frontal pose, tap **Capture and enroll**. The button disables while processing. Expect an automatic return to **Staff Profile**, “Face enrollment saved successfully,” **Face Enrolled**, a last-enrolled time and **Re-enroll Face**. Return to the list: the same staff row must show **Face Enrolled**. The other staff member remains unenrolled.
7. Force-stop AttendAI (Android Settings → Apps → AttendAI → Force stop), reopen and sign in again. Open Alex Demo. Name, employee ID, **Face Enrolled** and enrollment time must still be present. You can also restart the emulator and repeat. Authentication remains intentionally in memory, so signing in again is expected.
8. Tap **Re-enroll Face** and capture again after a few seconds. Expect the same staff ID/row and a newer last-enrolled time, with no extra list row. Repeat the force-stop/reopen check. The real Room instrumentation test additionally verifies that replacement changed the stored vector.
9. On re-enrollment, point the camera at an empty scene, then at two visible faces. Expect a useful detection error and no success navigation. Return to the profile: the prior enrollment/time must remain. Retry with one face. Test rapid capture taps; they must not create simultaneous writes. If using the synthetic camera, “No face detected” is expected and cannot complete enrollment.
10. Rotate the emulator during profile/enrollment and confirm it remains usable. Sign out and sign back in: staff records persist. Staff authentication remains unavailable. The Debug POC is optional and its in-memory reference remains separate from persisted staff enrollment.

Optional database inspection while the debug app is running: Android Studio → App Inspection → Database Inspector → `attendai.db`. Query:

```sql
SELECT id, employeeId, name, length(faceEmbedding) AS embeddingBytes,
       faceModelId, faceEnrolledAt
FROM staff;
```

Expect `embeddingBytes = 512` for enrolled rows and null for unenrolled rows. No selfie path or attendance table exists.
